AI Agent Observability · Part 2

The Three Pillars of AI Agent Observability: Trace, Metrics, Evaluation

July 4, 2026 · 18 min read

See what it did, quantify how it ran, judge whether it got things right.

This is the second article in the AI Agent Observability series. Part 1 answered "why traditional APM isn't enough"; this one answers the next question: in the age of agents, why aren't logs, metrics, and traces alone enough — and what exactly should we observe?

1. From "the system isn't broken" to "did the agent get it right?"

Part 1 came down to a single sentence: traditional APM can see whether "the system is broken," but not necessarily whether "the agent got it right."

Which leads naturally to the next question—

If an agent's failure doesn't necessarily show up as an error code, a timeout, or a crash, then what exactly should we observe?

The answer isn't "add a few more log lines" or "stand up another dashboard." To get this right, we first split "what to observe" into three questions that can't substitute for one another:

What you want to know The capability
What did the agent actually do this time? Trace
How is it performing across many runs? Metrics
Was the output actually correct? Evaluation

These are the three pillars of this article. Remember their division of labor in one line:

Trace records behavior, Metrics quantify operation, Evaluation judges quality.

Two honest caveats first

First, "three pillars" is this article's explanatory framework — not official terminology.

OpenTelemetry doesn't use the word "pillars." It uses signals — currently supporting Traces, Metrics, Logs, and Baggage, with Events, Profiles, and others still in development or proposal stages[1]. So strictly speaking: "three pillars" is a framework we've built to explain agent observability; in OpenTelemetry's own vocabulary, Traces, Metrics, and Logs are telemetry signals. Whenever we say "pillar" below, we mean it in this framework sense.

Second, listing Trace / Metrics / Evaluation as the three pillars does not mean Logs are thrown away.

Sharp-eyed readers will notice: the classic "three" are Logs / Metrics / Traces — so why did Logs turn into Evaluation here?

This isn't to say logs don't matter in agent systems. Logs are still the bedrock evidence for auditing, exception recording, security tracing, and debugging — and in LLM settings, many platforms organize tracing as "a structured record of every request," capturing the prompt, model response, token usage, latency, and the tool and retrieval steps in between[2].

The precise way to put it:

Logs remain the bedrock evidence; Trace / Metrics / Evaluation are the upper-layer framework this article uses to organize agent observability.

We focus on these three because they map onto the three questions that matter most in the age of agents — and that traditional monitoring is most likely to miss. Let's take them one at a time.

2. A running example: a refund support agent

To keep the three pillars from staying abstract, we'll use one fictional — but very realistic — example throughout the next three sections.

User: I was double-charged last week, please refund me.

Handling this, a single agent run roughly goes through:

  1. Understand the user's intent (this is a "refund request");
  2. Retrieve the refund policy (can it be refunded, and how);
  3. Query the order system (confirm the double charge really happened);
  4. Judge whether it meets the refund conditions;
  5. Call the refund endpoint (refund API);
  6. Generate a reply to the user;
  7. Get judged by an evaluation system: did this run actually get the job done right?

Hold onto these seven steps. Coming up:

  • Trace shows what happened at each step of this one run;
  • Metrics show how many such refunds perform in aggregate;
  • Evaluation judges whether this one answer and outcome were actually correct.

3. Trace | The fact layer: seeing the behavior chain of one agent run

Of the three pillars, Trace is the fact layer — it records how a single agent run actually unfolded. Without it, every later judgment has nothing to stand on.

1. Same structure as APM, but the semantic center of gravity shifts

An agent's trace reuses APM's trace / span structure, but what goes inside changes:

An APM trace tracks: which services a request passed through.

An agent trace tracks: which actions the agent took to reach its goal.

An APM span cares about "service A called service B, took X ms, errored or not"; an agent span focuses on behavioral semantics — prompt, model response, token usage, tool calls, retrieval steps.

⚠️ A caveat: prompts and model responses often contain user data, PII, or commercially sensitive information. In real production, these are usually sampled, redacted, truncated, or recorded only as summaries / reference IDs per your security policy — not logged in full plaintext unconditionally.

2. It's a "behavior tree"

Back to the refund example. One run's trace looks roughly like this:

Agent Run: refund_request
├── User input
├── Intent understanding
├── Retrieval: refund policy
├── Tool call: query_order
├── Tool call: create_refund
├── Model response: draft the reply
└── Evaluation result: did this count as success?

This tree lets you, for the first time, replay an agent run: what it retrieved at which step, which tool it called, what arguments it passed, what came back, and at which step it started going off the rails.

(This is only a schematic — no real field names. What fields a trace should actually record in the standard is the subject of the next article.)

3. Echoing Part 1: behavioral evidence, not an inner monologue

Part 1 stressed one line, and it's worth repeating here because it's the key to understanding Trace:

A trace lets us see the agent's behavioral evidence — not read the model's "inner monologue."

Observability can't read what the neurons are thinking; what it can do is fully record the externally visible behavior — which path it took, what context it used, which tools it called. Judging "right or wrong" is the job of the third pillar, Evaluation; Trace only lays out "what happened," faithfully, in front of you.

4. Metrics | The trend layer: quantifying performance, cost, stability, and behavior

Trace is right for single-run questions; but you can't page through traces one by one. To see "how many refunds perform in aggregate," you need Metrics — aggregating a flood of runs into trends.

Agent metrics fall into three layers, which is clearer than a simple "old vs. new" split:

Type Example metrics Notes
Inherited from APM End-to-end latency, throughput, error rate, resource saturation Still needed — to tell whether the service itself is stable
Reshaped for agents Latency split into model / tool / retrieval latency, retry count Still operational metrics, but must be broken down to each agent step
Agent-native (new) Token usage, cost per run, tool-call count, loop count, aggregated retrieval hit-rate & relevance scores, context usage For watching cost, behavioral anomalies, and quality risk

Note: quality signals like "retrieval relevance" are usually first produced as scores by rules, model evaluation, or human annotation, then aggregated into Metrics to watch trends — they straddle Metrics and Evaluation.

That middle layer deserves attention. Take latency: traditional APM latency is "one API's response time" — a single number is enough; but one refund task may involve several model calls, several tool calls, retrieval, and retries, so agent latency must be broken apart — is it slow in the model, the tools, or retrieval? Without splitting it, you only know "it's slow," not "why."

This section connects directly to Part 1's unit economics:

In an agent system, the cost of a single task comes not just from CPU and memory, but from tokens, model calls, tool calls, retrieval, and retries. So Metrics aren't only stability metrics — they're unit-economics metrics too.

Back to the refund example, Metrics should be able to answer:

  • On average, how many tools does one refund task call?
  • What's the p95 end-to-end latency? Which tool is slowest?
  • How many tokens — and how much money — does an average refund burn?
  • Is "loop count" spiking abnormally — some requests where the agent goes in circles?

(OpenTelemetry defines Metrics as "a measurement captured at runtime"[1]; Langfuse also explicitly recommends tracking cost and token usage[2]. These are the public basis for an agent metrics system.)

5. Evaluation | The judgment layer: did it get it right?

The first two pillars can tell you whether the agent is fast, cheap, and stable. But none of them can answer the deadliest question — like the scenario from Part 1: a support agent that confidently fabricated a refund policy that didn't exist, with normal latency, no errors, healthy resources, and only the answer wrong.

Metrics tell us how the agent is running; Evaluation tells us whether it got things right.

That's Evaluation's place. And here we have to be very careful about its relationship to traditional tooling — it isn't a replacement for traditional monitoring, but a quality-judgment layer newly promoted to first-class citizen in the age of agents.

One more thing to be clear about: Evaluation isn't a "truth machine." It works given business rules, reference answers, a rubric, or tool return values, turning "right or wrong" into a repeatable, traceable, regression-able judgment process — it doesn't inherently possess absolute truth.

1. How it differs from traditional "quality" tooling

Traditional APM / SRE has long had plenty of "quality and experience" concepts. Evaluation isn't out to deny them — it fills the gap they can't reach:

Traditional tool What it measures Difference from Agent Evaluation
SLO / SLI Whether service targets are met Mainly service performance — availability, latency, error rate
Synthetic Monitoring Whether a scripted path works Suits deterministic assertions; open-ended LLM output often has no single correct answer, hard to judge quality by script alone
Apdex / RUM User experience or performance satisfaction Mostly an experience proxy; doesn't directly verify whether an answer is factually right
Business KPI Business-outcome trends Can measure outcomes, but usually can't explain why a single output was wrong

They mostly measure service performance, user experience, or business outcomes. Whereas—

Agent Evaluation measures whether a single output, or the completion of a single task, is itself correct, complete, relevant, grounded, and compliant with policy and safety requirements.

2. The kinds of evaluation

Evaluation isn't a single scoring method. Using the refund agent, it splits into five kinds:

Evaluation type What it checks Example in the refund case
Rule-based Format, fields, banned words, schema Does the reply include the refund ticket number?
Code-based Programmatically verifiable results Did the refund API actually return success?
LLM-as-a-Judge Semantic quality, completeness, relevance Does the reply clearly explain the refund conditions?
Human review High-risk, complex business judgment Should a large refund recommendation get human sign-off?
Multi-turn Whether a multi-turn task truly completes Did the user ultimately get the correct outcome?

(Take Langfuse's evaluation docs as an example: they combine LLM-as-a-Judge, human annotation, and custom evaluation workflows to measure dimensions like quality, tone, factual accuracy, and completeness[3].)

🔗 Part 4 will dig into LLM-as-a-Judge specifically: how it scores, when it's reliable, and when it goes off the rails.

3. Evaluation is the entry point to a loop

The last point is the most important. Evaluation's value isn't just scoring one answer:

It settles failure cases into datasets, and turns problems surfaced in production into offline, regression-able tests.

That is, evaluation can score real traces online, and it can also run offline before release; valuable examples get collected into datasets, used to run experiments, compare changes, and keep the next release from re-breaking what was already fixed[3]. This sets up the "loop" in the next section.

6. How the three form a loop: the endpoint isn't a dashboard

With all three pillars covered, their real power isn't in existing separately — it's in stringing into a loop:

Metrics spot a trend        (refund success rate suddenly drops / cost doubles)
      ↓
Trace  locates the runs     (which batch of requests, stuck at which step)
      ↓
Evaluation judges right/wrong  (should these outputs count as failures?)
      ↓
Failure cases enter a Dataset  (settled into a reproducible test set)
      ↓
Fix prompt / tools / model / workflow
      ↓
Keep observing next round   (verify the change actually made things better)

This is why we say: the endpoint of agent observability isn't a pretty dashboard, but a continuous-improvement loop.

The one sentence to remember from this article:

Without Trace, an evaluation of an online failure often lacks process evidence; without Metrics, Trace lacks a global view; without Evaluation, observability can only tell you "what happened," not "whether it was any good."

Three pillars — drop any one, and the loop breaks.

7. Getting started: what to collect first

⚠️ This section is experience-based advice, not an industry standard. If you're building agent observability from scratch, you can fill it in in this order rather than turning everything on at once.

Stage Suggested to collect Purpose
Day 1 trace_id / session_id, agent name & version, model name, prompt version, input/output tokens, latency, tool name / args / result / error, final answer, a basic technical success/failure label (plus an optional business success/failure label) Make a single run replayable and locatable
Week 1 Cost per run, retry count, loop count, retrieval query & retrieved doc IDs, whether escalated to human, failure category, a simple evaluation score Make trends and failure modes analyzable
Maturity Multi-turn evaluation, multi-agent handoff traces, long-term memory read/write, online evaluation sampling, trace-to-dataset conversion, CI regression evaluation Enter the continuous-improvement loop

The principle in one line: don't chase completeness on day one — first make a run replayable and scorable, then build up from there.

8. Closing: next up, the OpenTelemetry GenAI standard

By now we have the basic framework of AI Agent observability:

Trace records behavior, Metrics quantify trends, Evaluation judges quality.

But one question remains — in what standard format should these signals actually be expressed?

If every framework, every platform, and every team defines its own fields, agent observability will quickly turn into a pile of new data silos: the trace you record on platform A becomes unreadable on platform B.

So the next article enters the OpenTelemetry GenAI semantic conventions: what an LLM call, a tool call, and an agent invocation should actually look like in the standard.

The framework is in place; next, we give it a shared language.
