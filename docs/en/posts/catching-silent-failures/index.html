Catching Hallucinations, Loops, and Cost Runaways: Alerting on Silent Failures

July 15, 2026 · 15 min read

Just because your agent didn't throw an error doesn't mean it hasn't gone off the rails. Here are three silent failures and how to alert on them.

This is Part 5 of the AI Agent Observability series. Over the last four parts, we explored how to read a trace and how to use an LLM-as-a-Judge to score answers. But for an architect or SRE carrying a KPI, you can't stare at tens of thousands of traces every day. Today, we will aggregate the raw data (Telemetry) accumulated in the first four parts into system signals that can trigger Alerts and standard operating procedures (Runbooks).

1. An Out-of-Control Agent with No Errors

💡 Establishing Boundaries First: The refund support scenarios, call counts, token volumes, and costs mentioned in this article are simplified, synthetic engineering examples used to illustrate observability methodologies. They do not correspond to any real customer production incidents.

Let's return to that extremely thorny Refund Support Agent scenario. In its second month post-launch, the month-end review surfaced three deeply problematic agent runs:

  1. The First Request: The underlying tool clearly couldn't find the order, but the large model returned an unsupported success confirmation, replying, "Your refund has been processed."
  2. The Second Request: The model couldn't find the order, and entered repeated retries, calling the query tool 15 times using order_id="null", "none", and "0" before finally stopping.
  3. The Third Request: The task was completed, but for a simple Q&A, the agent repeatedly dumped the entire irrelevant knowledge base into the context, burning 8,500 Input Tokens in a single request—making the cost 10 times the baseline.

In a traditional APM dashboard, these three requests might all still return HTTP 200. They might not even trigger traditional Error-Rate alerts. Even if some triggered latency alerts, traditional APM usually cannot directly explain the model's erroneous behavior and the resulting business outcome.

This is the core engineering pain point we face: Production incidents in Agent systems often do not manifest as explicit Errors; instead, they show up as wrong answers, ineffective behavior, or quietly inflating unit costs.

To catch them, we must seamlessly graft the classic Site Reliability Engineering (SRE) framework onto AI observability.

2. From Trace to Signal: Not Every Chart Deserves an Alert

The biggest fear of a monitoring system isn't a lack of data; it's "Alert Fatigue" caused by too much data. If you attach a phone call alert to every low score from an LLM Judge, your On-Call engineers will eventually break down.

To manage Agents well, you must build a strict funnel (from the bottom up):

  • Telemetry: The Traces, Spans, and Events we collect. This is the evidence.
  • Signal: A combination of observed facts that strongly explain a failure (e.g., Tool Error + Reply Judged as Success = False Success Signal).
  • SLI (Service Level Indicator): A metric that can be continuously measured over time (e.g., the occurrence rate of False Success events).
  • SLO (Service Level Objective): The internal target you hope to maintain for an SLI within an agreed time window.
  • Alert: Triggers a notification, ticket, or page when a predefined condition indicates material user impact, business risk, or significant error-budget consumption.
  • Runbook: The playbook detailing what charts a human should look at and what scripts they should execute after an alert triggers.

⚠️ Core Principle: Not every trace attribute is worth becoming an SLI, and certainly not every SLI breach requires an immediate page.

Below, we will design three "detectors" to turn the Raw Traces discussed in the first four parts into highly valuable Signals in the funnel above.

📦 Open Source Companion Code: The rule detectors, synthetic Trace test sets (JSON), metric calculation examples, and Prometheus alert rules (YAML) covered in this article have been integrated into a fully runnable Demo repository. The core demo uses precomputed evaluation scores and can run without calling an LLM API; re-running the Groundedness Judge requires a separately configured local model or compatible API: 👉 GitHub: ai-agent-observability-labs/05-signals-slos-alerts

3. Signal 1: How to Detect Hallucinations and "False Successes"

The biggest trouble with large models is their tendency to "package errors." In the first case of Section 1, how do we catch it?

Never say, "If the LLM Judge gives this text a low score, it's a hallucination; alert immediately." This single-point judgment is extremely fragile. Industrial-grade "False Success" detection requires cross-verification of multi-dimensional data:

  1. Deterministic Rules: Track if the underlying tool execution failed (Span error=true).
  2. Semantic Judge: The Groundedness judge mentioned in Part 4 gives a Fail(0), meaning the reply content is not supported by the tool's results.
  3. Business Verification: Combined with external DB state, the refund transaction was indeed not created.

(Note: The business-side verification does not require calling an expensive LLM API. As long as your observability backend associates the above metrics when collecting Traces, a minimal Python rule can filter this out offline or asynchronously.)

def detect_false_success(trace: dict) -> bool:
    """ Rule: Tool Error + Groundedness Score 0 + DB Not Successful """
    has_tool_error = any(span.get("error") for span in trace.get("spans", []))
    groundedness_failed = trace.get("evaluations", {}).get("groundedness_score") == 0.0
    business_failed = trace.get("business_state", {}).get("db_refund_status") == "FAILED"

    return has_tool_error and groundedness_failed and business_failed

A Judge Fail is a high-value risk signal, but it must be combined with tool status and business facts to identify a "False Success" event with higher confidence; as for whether the root cause is model generation, orchestration logic, or flawed error handling, you still need to look at the Trace.

4. Signal 2: How to Identify Infinite Loops with No State Progression

Because Agents can autonomously invoke tools (Tool Calling), they easily fall into "infinite loops." But how do you define an infinite loop?

⚠️ An infinite loop is not "too many steps"; it is "steps that bring no progression in state."

A long task might need to call 10 different tools; that's exploratory behavior.
A legitimate retry might switch parameters and call again after 3 seconds due to a network timeout; that's a fault-tolerance mechanism.

The characteristics of a true Suspected Loop are:
Same tool + Same or highly similar parameters + Consecutive Errors + Repeated within the same Trace window + No state progression.

Below is a simplified candidate loop detector (it only checks for consecutive failures of the same tool).
(Note: It is only used to filter suspected loops at a low cost in the backend Trace stream; a true production implementation should also add parameter similarity normalization and state progression verification to avoid flagging reasonable error-exploration mechanisms.)

def detect_loop(trace: dict, loop_threshold: int = 3) -> bool:
    """ Simplified Logic: Consecutive calls to the [same tool], consecutive [errors] """
    consecutive_errors = 0
    last_tool_name = None

    for span in trace.get("spans", []):
        if span.get("gen_ai.operation.name") == "execute_tool":
            current_tool = span.get("gen_ai.tool.name")
            is_error = span.get("error", False)

            if current_tool == last_tool_name and is_error:
                consecutive_errors += 1
            else:
                consecutive_errors = 1 if is_error else 0
                last_tool_name = current_tool

            if consecutive_errors >= loop_threshold:
                return True
    return False

Once the above logic evaluates to True in the backend's asynchronous observability stream, it should be used as a high-quality signal to trigger alerts and reviews; if this logic runs upfront in a Runtime Guardrail, it can directly intercept the request and Handoff to a human agent, cutting your losses immediately.

5. Signal 3: How to Identify Cost Runaways

In the previous four parts, we mentioned that a single Agent run generates underlying attributes like gen_ai.usage.input_tokens (OpenTelemetry GenAI Standard)[1]. But simply charting this is meaningless.

Detecting cost runaways requires aggregating upwards across three levels:

Aggregation Level Metric Name Core Problem Solved
Single Span input/output tokens, model latency Finds out which model call is the most expensive or slowest.
Single Agent Run total tokens, tool calls, estimated cost Finds out which user interaction was the most expensive.
Business Dashboard Cost per Successful Task Did the money spent actually buy business success?

Remember, for Agents aimed at task completion, Cost per Successful Task (the average cost of an effective task) is one of the unit-economic metrics most worthy of prioritization.
Why? Because low cost with massive task failures (like constantly refusing to answer) has zero business value; whereas if a single run consumes thousands of tokens but successfully resolves a high-net-worth, complex customer complaint, that money is well spent.

6. From Metrics to Auxiliary SLOs

With the three solid Signals above, we can push them to the SRE dashboard and establish auxiliary SLOs (Service Level Objectives) for the Agent.

Below is an enterprise-grade configuration example:

Dimension SLI (Service Level Indicator) Auxiliary SLO (Tolerance Target)
Coverage Groundedness Coverage Rate
(eligible high-risk runs that completed groundedness scoring / all eligible high-risk runs)		 At least 20% of high-risk online requests complete asynchronous evaluation.
Quality Groundedness Pass Rate pass / (pass + fail) > 99.0%
Anomaly Abstain / Handoff Rate Maintain a stable human-handoff rate without continuous abnormal spikes.
Behavior Loop-Free Run Rate 99.9% of requests do not trigger the Loop detector.

Red Line Warning: These metrics are currently only suitable as Release Gates or operational reference metrics within the enterprise. Until the judge system is stable enough and the human calibration rate is high enough, do not blindly use them as Hard SLOs for external commercial commitments.

7. Alert Design: Avoiding Agent Alert Storms

When writing alert rules (like in Prometheus pseudo-code), you must follow the iron law of SRE: Page on symptoms, investigate causes (page based on the final symptom, use Trace to find the cause)[2].

⚠️ Remember: Never put the full Prompt text, or a high-cardinality User_ID, into the Metric Label of an alerting system for aggregation. High-cardinality labels will significantly increase the number of time series, causing excruciatingly slow queries and driving up storage costs. Alert notifications should only contain low-cardinality dimensions, the Trace ID, or controlled troubleshooting links.

We typically design three types of alerts:

💡 Tip: The events, windows, and thresholds below (like $1, 5%) continue to use fictional numbers purely to demonstrate alert tiering and PromQL expressions; true production thresholds must be calibrated against the historical baseline and minimum sample size of the Use Case.

1. Single Critical Event Alerts (Page Immediately)

Examples: Unauthorized tool calls, violating a Safety Policy Judge, or a single Trace fee abnormally exceeding $1 (preventing bankruptcy).

2. Sliding Window Trend Alerts (Follow up during Business Hours)

Example: In the past 15 minutes, the proportion of requests triggering detect_loop spikes above 5%. This often isn't a model-only failure; it's the upstream business API going down, causing the model to enter repeated retries.

(Note: The following is just a conceptual PromQL snippet to demonstrate core logic; a real production rule requires a for duration, appropriate label grouping, and clamp_min to prevent false positives when the denominator is too small during low traffic[3].)

- alert: AgentLoopRateHigh
  expr: |
    sum(rate(agent_signal_suspected_loop_total[15m]))
    /
    clamp_min(sum(rate(agent_run_total[15m])), 0.001)
    > 0.05
  for: 10m
  labels:
    severity: warning
  annotations:
    summary: "Agent suspected-loop rate is elevated"
    runbook_url: "https://internal.wiki/runbooks/agent-loop"

3. Burn-rate Alerts vs. Cost Budget Consumption

For clear good/bad events (binary judgments) like Groundedness Pass Rate, you should apply Google SRE's classic Error-Budget Burn-Rate model[4]: a sharp deterioration within a short window triggers a high-priority alert, while slow degradation over a long window goes into a standard ticketing queue for investigation.
However, for Cost per Successful Task, the more accurate approach is to monitor its Cost Budget Consumption Rate or its abnormal deviation against a historical baseline of the same version, rather than blindly applying the reliability error-budget formula.

8. Runbooks and the Improvement Loop: Where Do Alerts End?

When an On-Call engineer gets the AgentLoopRateHigh alert above at 2 AM, they absolutely shouldn't just see a dry "Something went wrong."

Every high-quality alert must include a link to a Runbook (Standard Operating Procedure)[2].

A standard Agent incident response loop should look like this:

  1. Click the alert notification and jump directly to the relevant Trace ID.
  2. Based on the Trace, determine the root cause: is it a model version change, an abnormal Context assembly, degraded retrieval quality/knowledge source issues, or an underlying business tool crash?
  3. Take emergency action: Roll back, temporarily disable the tool, or force a Handoff to humans.
  4. The most critical step: Extract the key input trajectory of the failed Trace—after redaction, minimization, and human confirmation—and curate it into a reproducible Dataset item (Regression Test Case)[5].
  5. Before trying to fix the issue and passing the release gate next time, use offline Evaluation to confirm this same loop doesn't happen again.

The endpoint of an alert is never merely having an on-call engineer dismiss an "Acknowledged" notification.
The endpoint of an alert is to permanently solidify silent production failures into automated test cases that cannot be bypassed in the next release.
