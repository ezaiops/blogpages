AI Agent Observability · Part 3

Understanding an Agent Trace: Decoding OpenTelemetry GenAI Semantics

July 6, 2026 · 12 min read

You can't "catch the killer" by guessing. When LLM free will is injected into code, debugging no longer starts with logs — it starts with traces.

This is the third article in the AI Agent Observability series. In the first two parts, we established the Trace, Metrics, and Evaluation framework. Today, we're finally looking at the real thing: tearing open the black box to see what an agent's execution trace actually looks like.

1. A Story First: A "Flawless" Customer Complaint

In the first week your refund support agent goes live, you receive an angry customer complaint:

User: "I asked for a refund three days ago. Your AI told me 'refund processed,' but I still haven't seen a dime!"

As the owner, you immediately open your traditional APM dashboard and pull up that request using the session_id. The results make you frown:

  • The HTTP gateway returned 200 OK.
  • The order database had no slow queries or deadlocks.
  • Container CPU and memory were completely normal.
  • The error log was spotless.

In the worldview of traditional monitoring, this was a perfect, healthy, flawless request. But the business transaction definitely failed — the money wasn't refunded.

To get to the bottom of it, you open your newly integrated Agent Observability platform and pull up the Trace for that request. The truth is immediately obvious.

2. The Crime Scene: An Agent Behavior Tree

💡 Setting boundaries first: For ease of understanding, the trace below has been anonymized and simplified. It's not raw JSON exported directly from a tool, but rather the core structure typically presented in an observability dashboard for a production-grade agent trace.

In the observability dashboard, you see a "behavior tree" nested with multiple spans. This is the true execution path of that refund request:

Trace: refund_agent_run (Total Duration: 3.2s)
├── 🔵 chat.completions (Model: gpt-4o)          [800ms]
│   ├── Prompt: "User requesting refund, order ID 12345..."
│   └── Output: ToolCall(name="query_order")
├── 🟢 execute_tool: query_order                 [150ms]
│   ├── Input: {"order_id": "12345"}
│   └── Output: {"status": "paid", "amount": 99.0}
├── 🔵 chat.completions (Model: gpt-4o)          [1.1s]
│   └── Output: ToolCall(name="create_refund")
├── 🔴 execute_tool: create_refund               [50ms] ❌ ERROR
│   ├── Input: {"order_id": "12345", "amount": "full"}
│   └── Output: "TypeError: amount must be a number"
└── 🔵 chat.completions (Model: gpt-4o)          [1.1s]
    └── Output: "Your refund has been processed, please check your statement in 3 days."

You found the killer. This is a classic chain-reaction crash involving semantic failure and hallucination:

  1. First model call: The agent performed well, deciding to check the order first (query_order).
  2. Second model call: The agent decided to issue the refund. But when assembling parameters, the LLM took liberties, filling the amount field with the string "full" instead of the number 99.0 required by the API.
  3. Tool execution error: The underlying create_refund tool was a strict Python function that promptly threw a type error.
  4. The fatal misstep: The LLM received the context of the tool error, but its subsequent generation failed to properly surface this failure. Instead, it hallucinated a reassuring response: "refund processed."

This is why the HTTP status was 200, but the business failed.

Without a trace to record every prompt generated by the model, as well as the inputs and outputs of tool calls, bugs like this — occurring in the spaces between different LLM reasoning nodes — are fundamentally impossible to investigate.

3. Peeling the Onion: How OTel Expresses Agent Behavior

You understand the tree above, but there's an engineering problem: If every framework defines its own custom data format, your monitoring dashboard won't be able to piece this tree together.

This is why the industry needs the OpenTelemetry (OTel) GenAI semantic conventions. They provide a shared "lingua franca": enabling different frameworks, SDKs, and backends to use consistent semantics when describing model calls, tool calls, token usage, and errors.

To understand OTel's approach, we can simplify that failed tool call from above into a "pseudo-OTel span" structure.

⚠️ Note: This is a teaching illustration that preserves the core structural relationships of Span / Attributes / Events. Do not copy these exact field names directly into production code. Real fields (like gen_ai.tool.name vs tool.name) will change based on OTel versions and specific instrumentation implementations. Always defer to the current spec and your library's documentation.

{
  "name": "execute_tool create_refund",
  "kind": "INTERNAL",
  "context": {
    "trace_id": "5b8e9f...",
    "span_id": "9a1c3d..."
  },
  "attributes": {
    "gen_ai.operation.name": "execute_tool",
    "gen_ai.system": "example-agent-framework",
    "tool.name": "create_refund",
    "error.type": "TypeError"
  },
  "events": [
    {
      "name": "tool.input",
      "attributes": {
        "content": "{\"order_id\":\"12345\",\"amount\":\"full\"}"
      }
    },
    {
      "name": "tool.output",
      "attributes": {
        "content": "TypeError: amount must be a number"
      }
    }
  ]
}

In this structure, there are a few core concepts:

  1. gen_ai.operation.name: Defines what this step is doing. It's the skeleton of the entire analysis; common values include chat (model conversation) and execute_tool.
  2. Attributes: Static characteristics attached to this span. If it's a model call, this is also where crucial billing metrics live: gen_ai.usage.input_tokens and output_tokens.
  3. Events: Large blocks of text (like the JSON arguments of a tool call, or the long text generated by a model) are often unsuitable to stuff into attributes. Instead, they are attached to the span as timestamped events.

4. A Minimalist Approach: Low-Intrusion Instrumentation, Not "Magic Zero-Intrusion"

At this point, you might be worried: "Do I have to manually write span.start() and fill in all these JSON fields every time I call a model or write a tool function?"

The answer is: No. Increasingly, mainstream LLM/Agent frameworks can integrate with tracing via auto-instrumentation.

Taking LangChain / LangGraph in Python as an example, the code below illustrates the integration approach:

# Example: Package and class names vary by version, always refer to your library's docs.
# Note: It might be LangChainInstrumentor or LangchainInstrumentor

from opentelemetry.instrumentation.langchain import LangchainInstrumentor

# Enable the probe for "low-intrusion" tracing on business logic
LangchainInstrumentor().instrument()

# Then, continue writing your original Agent / Graph business logic
from langgraph.graph import StateGraph
# ...

After configuring the environment (such as enabling sampling and redaction policies), the instrumentation usually intercepts model calls and certain tool calls under the hood, capturing tokens and latency, and sending them to the observability backend. The actual scope of capture depends on the SDK, version, and configurations you use.

But this is not a cost-free "magic zero-intrusion" solution. When pushing it to production, you must navigate the three major pitfalls below.

5. The Production Survival Guide

1. PII, Data Privacy, and Content Capture Policies

Regarding the probe configuration above, we must clear up a massive misconception: Do not assume instrumentation is secure by default.

Default behaviors across different instrumentation libraries are inconsistent. Some implementations only capture metadata like model names and token consumption by default; but others (like opentelemetry-instrumentation-langchain) will capture complete prompts and model outputs by default.

⚠️ Red Line Warning: Prompts and model replies frequently contain real user names, credit card numbers, and company secrets.

Solution: In a production environment, you must explicitly verify the content capture toggles for your SDK/instrumentation (for example, configuring TRACELOOP_TRACE_CONTENT=false). If you want to see the tool arguments and prompt text we used to solve the case at the beginning of this article, you usually need to explicitly and safely enable that capture. And once enabled, before the data leaves your business servers, you must apply security policies to redact, truncate, or retain only data reference IDs. Sensitive info must never run naked in plaintext.

2. The High Cardinality Disaster

Never take the prompt text you send to an LLM, or dynamically generated user IDs, and use them as the span name or set them directly as indexable attributes.

Once indexable attributes attain extremely high cardinality (an infinite number of discrete values), the observability backend's database will immediately explode, queries will crawl at a snail's pace, and your bill will skyrocket.

Solution: Span names must be low-cardinality constants (e.g., chat, create_refund). Large blocks of text or dynamic content are much better suited to being placed in controlled events, external blob storage, or simply leaving a reference ID in the trace.

3. Full Traces vs. Storage Costs

Agent traces are often vastly larger than traditional API traces (containing multi-turn conversations, retrieved documents, and large JSON payloads returned by tools).

If all content is fully retained long-term, costs are prohibitive. A common practice in production is: retain 100% of failed requests, but sample successful requests. High-fidelity traces used for live troubleshooting are kept only for short periods, while only the failed samples that enter regression test suites (Datasets) are kept long-term.

6. Closing: You Can't Just Watch the Tapes

With tracing, it's like we've acquired a high-definition security tape of the crime scene. Now, we know clearly that the "refund processed" message didn't mean the refund succeeded, but was rather a flawed confirmation reply following a tool failure.

However, this leads to a massive engineering challenge:

We can't hire an army of people to visually inspect thousands of trace trees every day.

Since LLMs can wrap errors in fluent natural language, could we use another model to act as an automated quality referee?
