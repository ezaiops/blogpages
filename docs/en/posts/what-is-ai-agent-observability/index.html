AI Agent Observability · Part 1

What Is AI Agent Observability? Why Traditional APM Can't See That the Agent "Got It Wrong"

July 3, 2026 · 15 min read

This is the first article in the AI Agent Observability series. We won't talk about tools or code yet. Instead, we'll answer a more basic question: when software starts "making its own decisions," why does the worldview behind two decades of monitoring suddenly stop being enough?

1. A Story First: An Alert That Never Came at 3 A.M.

The following is a fictional scenario — but a thoroughly realistic one today.

Imagine you run a production system. At 3 a.m., your phone stays silent.

The dashboard is a wall of green: services up, response time 200 ms, error rate 0%, CPU and memory healthy. By every standard that operations teams have used for the last twenty years, this system is running flawlessly.

And yet, that very night, your newly launched AI support assistant confidently told more than three hundred users about a refund policy that does not exist. It didn't throw an error. It didn't time out. It didn't crash. To the server, every single one of those replies was a clean, successful request.

You only found out the next morning — from the complaints.

That's where this whole series begins. Traditional monitoring told you "the system isn't broken," while completely failing to tell you "the system got it wrong." For the first time in the history of software, those two things have come apart.

And that gap is exactly what AI Agent observability exists to fill:

Traditional APM asks — is the system broken?

AI Agent observability asks — did the agent get it right?

The former watches machine state; the latter watches behavioral quality. The former answers "is it fast, did it error, can it cope"; the latter answers "why did it do that, was it correct, and can it be continuously improved."

2. An Analogy for Everyone

If you don't write code, this analogy is all you need:

  • Traditional APM (Application Performance Monitoring) is like the dashboard in a car: speed, fuel level, engine temperature, warning lights. It monitors how well the machine itself is running.
  • AI Agent observability is like the driving instructor sitting in the passenger seat: the car is fine, there's plenty of fuel — but why did you turn at that intersection? Did you see that red light? Is this really the fastest route to the airport?

The dashboard cares about the condition of the car. The instructor cares about whether you're driving correctly.

Traditional software is the car: you press the gas, it moves, and the same action always produces the same result — so a dashboard is enough. But an AI Agent is that driver who makes its own judgments, picks its own routes, and occasionally, with great confidence, turns the wrong way. A dashboard alone falls far short.

3. So, What Is an AI Agent?

Before we talk about how to observe it, we need to be clear about what's being observed.

A traditional program is a hard-coded flow: if A then do B, else do C. Engineers spell out every step, and the program faithfully executes it.

An AI Agent is different. You give it a goal ("book me the cheapest flight to Shanghai tomorrow"), and it breaks down the task, makes judgments, and calls tools on its own (check flights, compare prices, place the order), stepping toward the goal. How it gets there isn't fully written out in advance by a human — it's something the model "figures out" at runtime.

This brings one revolutionary — and troublesome — property:

The same input can produce different outputs.

More precisely: for the first time, the core business decision path is being generated dynamically, at runtime, by a probabilistic model. This isn't the incidental non-determinism of traditional distributed systems — the kind that comes from concurrency, networks, or randomized algorithms. It's part of how an agent fundamentally works.

This isn't a bug. It's the nature of AI. And every observability challenge grows out of it.

One caveat, though: this doesn't mean an agent is ungovernable — it means we can no longer govern it with error codes, logs, and resource metrics alone. It needs a different way of being observed.

4. The Fundamental Difference: Five Broken Assumptions

Traditional APM rests on a handful of assumptions that are simply taken for granted. AI Agents break them one by one.

1. From "is the system healthy?" to "is the decision right?"

The core signals APM and SRE teams rely on are latency, traffic, errors, and saturation (Google SRE's "four golden signals"); in service monitoring, these are often distilled into the RED method: Rate, Errors, Duration. They all answer the same question: "Can the system still handle the load?"

But for an AI Agent, a single call can have normal latency, no errors, and healthy resources — and still be wrong. The 3 a.m. story is exactly that case.

So observability has to answer a question APM never needed to: did it get this one right? And "right" is usually not black-and-white — it's a quality distribution: was the answer accurate, complete, and free of fabrication?

2. From determinism to non-determinism

The open-source observability platform Langfuse puts its finger on the core issue in one line: AI is "inherently non-deterministic," and without dedicated tooling, debugging it is "more like guesswork."

The entire methodology of traditional monitoring is built on "same input → same output": when something breaks, you replay it to reproduce. But replay an AI Agent, and it may hand you a different answer. The old debugging paradigm doesn't hold up from the foundation.

3. From "tracing calls" to "tracing reasoning"

Traditional APM traces a call chain: a request goes from service A to service B to the database, and each hop takes so many milliseconds.

An AI Agent needs its reasoning chain — its behavior chain — traced. Note that observability can't actually read the model's neurons or explain what it was "thinking"; what it can do is record the externally visible evidence: given what context did the model choose this path? What documents did it retrieve? What arguments did it pass to a tool, and what came back? In a multi-step task, at which step did it start going off the rails? (In other words, observability gives you behavioral evidence, not an inner monologue.)

Worth noting — both use the same underlying technology. The industry standard OpenTelemetry is describing these new signals through its "GenAI semantic conventions": model calls, token usage, tool calls, and the key context around an agent invocation. In several implementations and examples we can already see span semantics like invoke_agent (invoke an agent) and execute_tool (execute a tool) — we'll unpack the exact fields and their maturity in Part 3. Traditional APM never had a concept like "invoke an agent."

In other words: observability isn't out to overthrow APM — it packs an entirely new vocabulary about the "thinking process" onto APM's skeleton.

4. From "resource utilization" to "token economics"

Traditional APM watches CPU, memory, and connection pools. An AI Agent has to watch a whole new set of cost metrics: how many tokens were consumed, how much each call cost, how much of the context window was used, whether the cache was hit.

An agent stuck in a loop, calling the same tool over and over, might never spike the CPU — yet burn hundreds of dollars in API fees overnight. This kind of "quiet runaway" is something APM probes simply cannot perceive.

Which means agent observability isn't just a reliability question — it's a unit-economics question: how many tokens, how many dollars, and how many tool calls did one task actually cost — and was it worth it?

5. From "crashes and timeouts" to "semantic failures"

Traditional failures are explicit: the service died, the request timed out, memory leaked. But an AI Agent has an entire class of brand-new, silent failure modes:

  • Hallucination — confidently stating false information (that support bot from the opening);
  • Infinite loops — calling the same tool repeatedly, unable to stop;
  • Tool misuse — wrong arguments, wrong format, wrong tool entirely;
  • Lost context — halfway through a multi-step task, forgetting what it was doing;
  • Retrieval poisoning — pulling the wrong documents, so everything downstream is wrong;
  • Jailbreaks / prompt injection — being manipulated by users into saying or doing what it shouldn't.

These failures rarely show up in the form APM is best at catching. Even when some of them eventually surface as higher latency or a rising error rate (a runaway loop, for instance, drives up call volume and cost), APM can usually only tell you "something is wrong" — not which reasoning step, which tool choice, or which stretch of context the agent actually went astray on.

5. One Table to See the Division of Labor

Dimension Traditional APM AI Agent Observability
Core question Is the request fast? Did it error? Can the system cope? Did the agent get it right? Why did it decide this way?
Primary subject Services, endpoints, resources, call chains Agent runs, tool calls, retrieval, memory, reasoning paths
Failure modes Crashes, timeouts, rising error rate, resource saturation Hallucination, tool misuse, lost context, infinite loops, jailbreaks
Core signals Latency, traffic, errors, saturation Quality, token cost, tool correctness, retrieval relevance, safety
Value boundary Keep the system running reliably Keep the agent's behavior trustworthy, explainable, improvable

The single most important sentence — and the core conclusion of this article:

AI Agent observability isn't a replacement for APM; it's the layer above it. In a real production system, you need both: APM keeps the machines and services from crashing, while observability keeps the agent's "mind" trustworthy. They're two floors of the same building, not an either/or.

Closing

The software industry spent twenty years perfecting the art of "monitoring a deterministic machine."

Now we're beginning to monitor something that thinks, makes mistakes, and will — with a straight face — make things up.

The age of the dashboard isn't over. But a new role has stepped onto the stage: the coach in the passenger seat, watching every decision the AI makes.

This series is about introducing that coach to you.

And it won't stay at the level of concepts. Ahead, we'll break AI Agent observability into three throughlines — Trace, Metrics, Evaluation — then land on the OpenTelemetry GenAI semantic conventions, on detecting hallucinations / loops / cost runaways, and on wiring up a real agent end to end. The goal isn't to build yet another monitoring dashboard, but to answer a far more practical question: how does an organization know that an agent in production is both running reliably and getting things right.
