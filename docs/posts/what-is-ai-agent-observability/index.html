AI Agent 可观测性系列 · 第 1 篇

什么是 AI Agent 可观测性:为什么传统 APM 看不见"做错了"?

2026 年 7 月 3 日 · 约 15 分钟阅读

这是《AI Agent 可观测性》系列的第一篇。我们先不谈工具、不谈代码,而是回答一个更根本的问题:当软件开始"自己做决定",我们过去那套监控系统的世界观,为什么突然不够用了。

一、先讲个故事:一个凌晨三点的报警

下面是一个虚构、但在今天非常现实的场景。

假设你负责一个线上系统。凌晨三点,你的手机没有响。

监控大盘上一片绿色:服务在线、响应时间 200 毫秒、错误率 0%、CPU 和内存都很健康。按照过去二十年所有运维的标准,这套系统完美运行。

但就在这一夜,你们那个刚上线的 AI 客服助手,一本正经地告诉了三百多个用户一条根本不存在的退款政策。它没有报错、没有超时、没有崩溃。每一次回答,在服务器眼里都是一次干净漂亮的成功请求。

第二天你才从客诉里知道这件事。

这就是全文的起点。传统监控告诉你"系统没坏",却完全没能告诉你"系统做错了"。这两件事,第一次在软件的历史上被彻底分开了。

而这,正是 AI Agent 可观测性要补上的那一块:

传统 APM 关心的是——系统有没有坏。

AI Agent 可观测性关心的是——Agent 有没有做对。

前者看机器状态,后者看行为质量;前者回答"快不快、错没错、扛不扛得住",后者回答"为什么这么做、是否做对、能否被持续改进"。

二、给所有人的一个类比

如果你不写代码,用这个类比就够了:

  • 传统 APM(应用性能监控),像是给一辆车装的仪表盘:时速多少、油量多少、水温高不高、发动机有没有报警灯。它监控的是这台机器本身运转得好不好。
  • AI Agent 可观测性,则像是坐在一位新手司机旁边的教练:车没坏,油也够,但——你为什么在这个路口拐弯?你看到那个红灯了吗?你这条路线是去机场最快的方式吗?

仪表盘关心的是"车况",教练关心的是"你开得对不对"。

传统软件是车:你踩油门它就走,同样的操作永远同样的结果,所以只需要仪表盘。而 AI Agent 是那个会自己判断、自己选路、偶尔还会自信地开错方向的司机——光有仪表盘,远远不够。

三、那么,什么是 AI Agent?

在讲"怎么观测"之前,得先说清楚被观测的东西。

传统程序是写死的流程:如果 A 就做 B,否则做 C。工程师把每一步都规定好了,程序只是忠实执行。

AI Agent(智能体)不一样。你给它一个目标("帮我订一张明天去上海最便宜的机票"),它会自己拆解任务、做出判断、调用工具(查航班、比价格、下订单),一步步逼近目标。中间怎么走,不完全由人预先写死,而是模型在运行时"想"出来的。

这带来一个革命性的、也是麻烦的特性:

同样的输入,可能得到不同的输出。

更准确地说:软件的核心业务决策路径,第一次开始由概率模型在运行时动态生成。这不是传统分布式系统里那种由并发、网络或随机算法带来的偶发不确定性,而是 Agent 工作方式本身的一部分。

这不是 bug,这是 AI 的本质。而所有的观测难题,都从这里长出来。

但要强调一句:这并不意味着 Agent 不可治理,而是意味着我们不能再只依赖传统的错误码、日志和资源指标去治理它——需要换一套观测方式。

四、本质区别:五个被打破的旧假设

传统 APM 建立在几个默认成立的假设上。AI Agent 把它们逐个打破了。

1. 从"系统健不健康"到"决策对不对"

传统 APM 与 SRE 常用的核心信号是延迟、流量、错误率、饱和度(Google SRE 的"四个黄金信号");在服务监控里,也常被简化成 RED 方法:请求速率(Rate)、错误率(Errors)、耗时(Duration)。这套指标回答的都是同一个问题——"系统还扛得住吗?"

但对 AI Agent,一次调用可以延迟正常、没有报错、资源健康,答案却是错的。开篇那个凌晨三点的故事,正是这种情况。

所以可观测性必须回答一个 APM 从不需要回答的问题:它这次做得对吗?而"对不对"往往不是非黑即白,而是一个质量分布——回答得准不准、全不全、有没有胡编。

2. 从"确定性"到"非确定性"

开源可观测性平台 Langfuse 一句话点破了要害:AI 是 "天生非确定的"(inherently non-deterministic),没有专门的工具,调试起来"更像是在猜"。

传统监控的整个方法论,都建立在"相同输入 → 相同输出"之上:出了问题,重放一遍就能复现。而 AI Agent 你重放一遍,它可能给你一个不一样的答案。旧的排障范式,从地基上就不成立了。

3. 从"看调用链"到"看推理链"

传统 APM 追踪的是调用链:请求从服务 A 到服务 B 再到数据库,每一跳花了多少毫秒。

AI Agent 需要追踪的是推理链 / 行为链。注意,可观测性并不能真的读懂模型内部的神经元、解释它"脑子里"在想什么;它能做的,是把外部可见的证据记录下来:模型是在什么上下文下选择了这条路径?它检索到了哪些资料?调用工具时传了什么参数、拿回了什么?在多步任务里,它是在哪一步开始跑偏的?(换句话说,可观测性给的是"行为证据",不是"内心独白"。)

值得注意的是——这两者用的其实是同一套底层技术。业界标准 OpenTelemetry 正在通过 "GenAI 语义约定"描述这类新信号:模型调用、Token 使用、工具调用,以及 Agent 调用过程中的关键上下文。在一些实现和示例里,我们已经能看到类似 invoke_agent(调用一个智能体)、execute_tool(执行一个工具)这样的 span 语义——具体字段和成熟度,我们会在第三篇专门拆解。而传统 APM 里,从来没有"调用一个智能体"这种概念。

换句话说:可观测性不是要推翻 APM,而是在它的骨架上,装进了一套全新的、关于"思考过程"的语义。

4. 从"资源利用率"到"Token 经济学"

传统 APM 盯的是 CPU、内存、连接池。AI Agent 要盯的是一组全新的成本指标:消耗了多少 Token、每次调用花了多少钱、上下文窗口占用了多少、缓存命中了没有。

一个陷入死循环、反复调用同一个工具的 Agent,可能不会让 CPU 飙升,却能在一夜之间烧掉你几百美元的 API 账单。这种"安静的失控",是 APM 探针根本感知不到的。

这也意味着,Agent 可观测性不只是稳定性问题,更是单位经济性(unit economics)问题:完成一次任务到底花了多少 Token、多少钱、多少次工具调用——以及,这一次到底值不值。

5. 从"崩溃与超时"到"语义性失控"

传统故障是显性的:服务挂了、超时了、内存泄漏了。而 AI Agent 有一整类全新的、静悄悄的失败模式:

  • 幻觉——自信地说出错误信息(就是开篇那位客服);
  • 死循环——反复调用同一个工具,停不下来;
  • 工具用错——参数错了、格式错了、调错了工具;
  • 上下文丢失——多步任务走到一半,忘了自己在干嘛;
  • 检索污染——找错了资料,导致后面全盘皆错;
  • 被越狱 / 提示注入——被用户诱导,说出或做出不该做的事。

这些失败,往往不会以传统 APM 最擅长捕获的形式出现。即使某些场景最终表现为延迟升高或错误率上升(比如死循环会推高调用次数和成本),APM 通常也只能告诉你"系统异常了",却很难解释 Agent 究竟是在哪一步推理、哪一次工具选择、或哪一段上下文使用上走偏的。

五、一张表看懂两者的分工

维度 传统 APM AI Agent 可观测性
核心问题 请求快不快?错没错?系统扛得住吗? Agent 做得对不对?为什么这么决策?
主要对象 服务、接口、资源、调用链 Agent 运行、工具调用、检索、记忆、推理路径
失败形态 崩溃、超时、错误率升高、资源打满 幻觉、工具误用、上下文丢失、死循环、越狱
核心信号 延迟、流量、错误率、饱和度 质量、Token 成本、工具正确性、检索相关性、安全性
价值边界 保障系统稳定运行 保障 Agent 行为可信、可解释、可改进

最关键的一句话,也是本文的核心结论:

AI Agent 可观测性不是 APM 的替代品,而是它的"上层"。在一个真实的生产系统里,两者缺一不可:APM 保证机器和服务不崩,可观测性保证智能体的"脑子"靠谱。它们是上下两层楼,不是二选一。

六、这个系列,接下来会聊什么

这篇是入口。我想把"AI Agent 可观测性"这件事,从为什么,一路讲到怎么做。后续计划包括:

  • ② 三大支柱:Trace、Metrics、Evaluation —— 观测一个智能体,到底要收集哪三类数据?为什么"评估(Evaluation)"会成为 Agent 可观测性的第三根柱子——它和传统 APM 里的 SLO、合成监控(Synthetic Monitoring)、用户体验指标又有什么不同?
  • ③ OpenTelemetry GenAI 语义约定拆解 —— 一次智能体调用,在标准里到底被记成了什么样?invoke_agent、execute_tool 这些 span 里都装了什么?
  • ④ 如何给"对不对"打分:LLM-as-a-Judge 实战 —— 当对错不再非黑即白,我们怎么用一个 AI 去评判另一个 AI?它靠谱吗?会翻车吗?
  • ⑤ 抓住幻觉、死循环和成本失控 —— 那些静悄悄的失败,具体怎么被发现、被报警。
  • ⑥ 工具选型地图 —— Langfuse、LangSmith、Arize Phoenix,和 Datadog、New Relic 这些老牌 APM 厂商的"向上生长",到底该怎么选。
  • ⑦ 从零搭一套:给一个真实 Agent 装上"教练" —— 一个端到端的动手实践。

结语

软件行业花了二十年,把"监控一台确定的机器"这件事做到了极致。

而现在,我们要开始监控一个会思考、会犯错、还会一本正经胡说八道的东西。

仪表盘的时代没有结束,但一个新的角色登场了——那位坐在副驾、盯着 AI 每一个决定的教练。

这个系列,就是想把这位教练,介绍给你。

这个系列不会只停留在概念层面。后面我会把 AI Agent 可观测性拆成 Trace、Metrics、Evaluation 三条主线,再落到 OpenTelemetry GenAI 语义约定、幻觉 / 死循环 / 成本失控的检测,以及一个真实 Agent 的端到端接入。目标不是再造一个监控大盘,而是回答一个更实际的问题:企业怎么知道一个 Agent 在生产环境里,既跑得稳,又做得对。
