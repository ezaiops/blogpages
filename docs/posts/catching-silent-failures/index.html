如何抓住幻觉、死循环和成本失控：静悄悄的失败怎么报警

2026 年 7 月 15 日 · 约 15 分钟阅读

Agent 没报错，不代表它没失控：三类静默失败的告警实战

这是《AI Agent 可观测性》系列的第五篇。在过去的四篇里，我们讲透了如何读一条 Trace，以及如何用 LLM 当裁判给回答打分。但对于一个背着 KPI 的架构师或 SRE 来说，你不能天天盯着几万条 Trace 看。今天，我们要把前四篇积累的原始数据（Telemetry）降维聚合，变成可以触发告警（Alert）和标准处理流程（Runbook）的系统信号。

一、一次没有报错的失控

💡 先立边界：本文提及的退款客服、调用次数、Token 量及成本均为简化的合成工程示例，用于说明可观测性方法，并不对应任何真实客户的生产事故。

让我们再回到那个极其棘手的退款客服 Agent 场景。上线第二个月，你在月底的复盘会上看到了三条非常不正常的运行记录：

  1. 第一笔请求：底层工具明明查不到订单，大模型为了“安抚”用户，硬生生回复了“退款已受理”。
  2. 第二笔请求：大模型像魔怔了一样，连续用 order_id="null", "none", "0" 反复重试调用查询工具 15 次才作罢。
  3. 第三笔请求：任务办成了，但因为 Agent 反复把全量知识库扔进上下文，导致一次请求烧掉了 8500 个 Input Token，成本是基准的 10 倍。

在这三个案例里，系统可能仍然返回 HTTP 200，甚至没有触发传统 Error-Rate 告警；哪怕部分场景触发了延迟报警，传统 APM 也通常无法直接解释大模型的错误行为和业务结果。

这就是我们面临的最核心的工程痛点：Agent 系统的生产事故，不一定表现为 Error，它可能表现为错误的回答、无效的行为，或者悄悄上涨的单位成本。

要抓住它们，我们必须把 SRE（站点可靠性工程）的那套经典体系，无缝嫁接到 AI 可观测性上。

二、从 Trace 到 Signal：不是所有图表都值得告警

监控系统最怕的不是没数据，而是数据太多导致的“告警疲劳（Alert Fatigue）”。如果你把 LLM Judge 的每一个低分都配上电话告警，你的值班工程师（On-Call）迟早会崩溃。

要管好 Agent，必须建立一层严格的漏斗（从底向上）：

  • Telemetry（原始遥测）：我们收集上来的 Trace、Span、Event，这是证据。
  • Signal（信号）：对故障有强解释力的观测事实组合（例如：工具报错 + 且回复判定成功 = 假成功信号）。
  • SLI（服务质量指示器）：可以随着时间持续度量的指标（例如：假成功事件的发生率）。
  • SLO（服务质量目标）：针对某项 SLI，希望在约定时间窗口内维持的内部目标（例如维持约定的退款任务忠实度及格率）。
  • Alert（告警）：当预定义规则表明用户影响、业务风险或错误预算消耗达到需要响应的程度时，触发通知、工单或寻呼。
  • Runbook（处理手册）：告警触发后，人应该看什么图表、执行什么脚本。

⚠️ 核心原则：并非每个 Trace 属性都值得成为 SLI，更不是每个 SLI 越界都要立即寻呼。

下面，我们就分别设计三个“探测器”，把前四篇讲到的 Raw Trace，变成上面漏斗中极具价值的 Signal（信号）。

📦 配套开源代码：本文使用的规则检测器代码、合成 Trace 测试集（JSON）、指标计算示例以及 Prometheus 告警规则（YAML），均已整合在完整可运行的 Demo 仓库中。主 Demo 可在不调用 LLM API 的情况下完全离线运行；如需重新执行 Groundedness Judge 打分，则需另行配置本地模型或兼容 API：👉 GitHub: ezaiops/ai_agents_observability_demo

三、Signal 1：如何发现幻觉与“假成功”

大模型最大的麻烦是会“包装错误”。在第一节的第一个案例中，我们怎么抓出它？

千万不要说“只要 LLM Judge 给这段文本打了低分，它就是幻觉，立刻告警”。这种单点判断极其脆弱。工业级的“假成功（False Success）”检测，必须是多维数据的交叉印证：

  1. 确定性规则：追踪到底层工具执行失败（Span error=true）。
  2. 语义裁判（Judge）：第四篇里提到的 Groundedness（忠实度）裁判打分为 Fail(0)，即回复内容没有被工具结果支撑。
  3. 业务核验：结合外部 DB 状态，退款流水确实未创建。

（注：业务侧判断不需要调用昂贵的 LLM API。只要你的可观测性后端在收集 Trace 时关联了上述指标，用一段极简的规则就能离线或异步筛选出来。）

def detect_false_success(trace: dict) -> bool:
    """ 规则: 工具报错 + 忠实度判 0分 + 业务库未成功 """
    has_tool_error = any(span.get("error") for span in trace.get("spans", []))
    groundedness_failed = trace.get("evaluations", {}).get("groundedness_score") == 0.0
    business_failed = trace.get("business_state", {}).get("db_refund_status") == "FAILED"

    return has_tool_error and groundedness_failed and business_failed

Judge Fail 是一个高价值的风险信号，但必须结合工具状态和业务事实，才能较高置信地确认这是一次“假成功”事件；至于根因是模型生成、编排逻辑还是错误处理缺陷，还需要继续查看 Trace。

四、Signal 2：如何识别无推进的死循环

Agent 因为能够自主调用工具（Tool Calling），极易陷入“死循环”。但如何定义死循环？

⚠️ 死循环不是“步骤太多”，而是“步骤没有带来状态的推进”。

一个长任务可能需要调用 10 个不同的工具，这叫探索行为；
一次合法的重试可能因为网络超时而在 3 秒后更换参数重调，这叫容错机制。

真正的死循环（Suspected Loop）特征是：
相同的工具 + 相同或高度相似的参数 + 连续的 Error 报错 + 在同一个 Trace 窗口内反复出现 + 没有状态推进。

下面提供一个最简化的候选循环探测器（仅检查同一工具连续失败）。
（注：它仅用于在后端的 Trace 流中低成本筛选疑似循环；真实的生产实现还应加上参数相似度归一化对比和状态推进校验，以防止误伤合理的错误探索机制。）

def detect_loop(trace: dict, loop_threshold: int = 3) -> bool:
    """ 简化版逻辑: 连续调用[同一个工具]，连续获得[error] """
    consecutive_errors = 0
    last_tool_name = None

    for span in trace.get("spans", []):
        if span.get("gen_ai.operation.name") == "execute_tool":
            current_tool = span.get("gen_ai.tool.name")
            is_error = span.get("error", False)

            if current_tool == last_tool_name and is_error:
                consecutive_errors += 1
            else:
                consecutive_errors = 1 if is_error else 0
                last_tool_name = current_tool

            if consecutive_errors >= loop_threshold:
                return True
    return False

一旦上述逻辑在后端的异步观测流中判定为 True，它就应当作为高质量信号用于触发告警、复盘；如果该逻辑被前置运行在 Runtime Guardrail（运行时护栏）中，则可直接拦截请求并移交给人工客服（Handoff），及时止损。

五、Signal 3：如何识别成本失控

前四篇我们提到，一次 Agent 运行会产生 gen_ai.usage.input_tokens 这样的底层属性（OpenTelemetry GenAI 标准）[1]。但仅仅把它画在图表上毫无意义。

成本失控的检测，需要分成三个层级向上聚合：

聚合层级 指标名称 解决的核心问题
单次 Span input/output tokens, model latency 查出哪一次模型调用最贵、最慢。
单次 Agent 运行 total tokens, tool calls, estimated cost 查出哪一条用户请求的交互最贵。
业务大盘 Cost per Successful Task 花的钱，到底有没有换来业务成功？

记住，对于以任务完成为目标的 Agent 而言，Cost per Successful Task（有效任务的平均成本）是最值得优先观察的单位经济性指标之一。
因为：低成本但大量任务失败（如疯狂拒答），毫无业务价值；如果单次消耗极高（几千 Tokens），但能把高净值的复杂客诉处理掉，这笔钱花得就不冤枉。

六、从指标到辅助 SLO

有了上述三个坚实的 Signal，我们就可以把它推上 SRE 的大盘，建立 Agent 的辅助 SLO（服务等级目标）了。

以下是一个企业级的配置样例：

💡 注意：下表纯为展示表达方式的虚构示例目标。具体阈值必须通过内部基线流量、风险容忍度和成本预算来校准。

维度 SLI（服务质量指示器） 辅助 SLO（容忍度目标）
覆盖 Groundedness Coverage Rate
(已完成忠实度评估的高风险 eligible runs / 全部高风险 eligible runs)		 至少 20% 的线上高危请求完成了异步测评
质量 Groundedness Pass Rate pass / (pass + fail) > 99.0%
异常 Abstain / Handoff Rate 弃权转人工比率维持稳定，不发生持续上升异常
行为 Loop-Free Run Rate 99.9% 的请求不触发 Loop 检测器
成本 Cost per Successful Task 单次成功退款的 P95 成本不超过业务批准预算上限

红线提醒：这些指标目前只适合作为企业内部的发布门禁（Release Gate）或运营参考指标。在裁判系统足够稳定、人工校准率足够高之前，请勿将其作为对外商业承诺的 Hard SLO。

七、告警设计：避免 Agent 告警风暴

在编写告警规则（如 Prometheus 伪代码格式）时，一定要遵循 SRE 的铁律：Page on symptoms, investigate causes（按最终症状寻呼，用 Trace 查原因）[2]。

⚠️ 切记：千万不要把完整的 Prompt 文本，或者具有高基数的 User_ID 放进告警系统的 Metric Label（指标标签）里去聚合。高基数标签会显著增加时序序列数量，导致查询极慢并推高存储成本。告警通知中只应放置低基数维度、Trace ID 或受控的排障链接。

我们通常设计三类告警：

💡 提示：以下事件、窗口和阈值（如 $1、5% 等）继续使用虚构数字，仅用于演示告警分级与 PromQL 表达方式；真实生产阈值必须按 Use Case 的历史基线和最低样本量来校准。

1. 单次严重事件告警（立即寻呼）

例如：越权工具调用、违反安全 Policy Judge、单次 Trace 费用异常超过 $1（防止破产）。

2. 滑动窗口趋势告警（工作时间跟进）

例如：在过去 15 分钟内，触发 detect_loop（死循环）的比例突增至 5% 以上。这往往不是大模型傻了，而是上游业务 API 宕机导致大模型疯狂重试。

（注意：以下仅为展示核心逻辑的 PromQL 概念片段，真实生产规则需加上 for 持续时间、合理的 label 分组，以及 clamp_min 防范低流量时分母过小引发误报[3]。）

- alert: AgentLoopRateHigh
  expr: |
    sum(rate(agent_signal_suspected_loop_total[15m]))
    /
    clamp_min(sum(rate(agent_run_total[15m])), 0.001)
    > 0.05
  for: 10m
  labels:
    severity: warning
  annotations:
    summary: "Agent suspected-loop rate is elevated"
    runbook_url: "https://internal.wiki/runbooks/agent-loop"

3. Burn-rate 燃烧率告警 vs. 成本预算消耗

针对 Groundedness Pass Rate 这种明确的好/坏事件（二值判断），应当套用 Google SRE 经典的 Error-Budget Burn-Rate（错误预算燃烧率） 模型[4]：短窗口内急剧恶化触发高优告警，长窗口缓慢劣化则排入普通工单调查。
但对于 Cost per Successful Task，更准确的做法是监控其成本预算消耗率（Cost Budget Consumption Rate） 或监控其相对于历史同版本基线的异常偏离，而不能直接硬套可靠性的错误预算公式。

八、Runbook 与改进闭环：告警的终点在哪里？

当值班工程师（On-Call）在凌晨两点收到上面的 AgentLoopRateHigh 告警时，他绝不应该只看到一句干瘪的“出错了”。

每一条高质量的告警，必须附带一条 Runbook（处理手册链接）[2]。

一个标准的 Agent 故障响应闭环应该长这样：

  1. 点开告警通知，一键跳转到相关的 Trace ID。
  2. 依据 Trace，确定故障根因：是模型版本变化、Context 拼装异常、检索质量/知识源异常，还是底层业务工具宕机。
  3. 采取应急措施：执行回滚、临时禁用该工具、或者强制触发转人工（Handoff）。
  4. 最核心的一步：将该失败 Trace 经过脱敏、最小化和人工确认后的关键输入轨迹，提取沉淀为可复现的 Dataset（回归测试用例）[5]。
  5. 下次尝试修复问题并通过发布门禁前，用离线 Evaluation 确认这个同类死循环没有再发生。

告警的终点，绝不是让值班人员在手机上点掉一个“已知悉”的通知按钮。
告警的终点，是把线上的静默失败，永远固化为下一次发布前无法逾越的自动化测试用例。
