AI Agent 可观测性系列 · 第 4 篇

怎么给“对不对”打分：从规则到 LLM-as-a-Judge

2026 年 7 月 9 日 · 约 18 分钟阅读

当 Agent 每天产生三万条 Trace 时，我们靠什么判断它做得对不对？

这是《AI Agent 可观测性》系列的第四篇。在第三篇中，我们通过一条 Trace 抓住了大模型掩盖错误的“犯罪现场”。但工程上的挑战随之而来：你不可能每天靠肉眼去翻看三万条 Trace 树。今天我们解决核心问题：如何给 Agent 的回答自动化打分。

一、开篇故事：三万条 Trace，怎么判？

退款客服 Agent 稳定运行了一个月。流量涨了，每天产生 3 万条 Trace。

作为系统负责人的你，陷入了深深的焦虑：

  • 看大盘：APM 面板上，延迟正常、P99 健康、HTTP 错误率是 0。
  • 看客服后台：人类客服依然每天能收到几十条愤怒的投诉——“你们的 AI 在胡说八道”。

传统排查方式已经彻底失效了。你无法逐条点开 Trace 去看；采样看，只能撞见冰山一角；而那些“HTTP 200 但业务做错”的幽灵请求，隐藏在海量的正常数据中。

Trace 只是“行为证据”，它无法自己站起来回答“对不对”。

要解决这个问题，我们必须建立一层全新的能力：Evaluation（评估）层。

但千万别以为 Evaluation 就是花钱调个大模型给文本打分那么简单。真正的生产评估体系，是一个从确定性到语义化的连续谱系。

二、评估的三层结构：确定性、程序化、语义化

如果你的团队一上来就用大模型去评估每一条日志，那你大概率会被高昂的账单和极慢的吞吐量拖垮。

一个健康、扛得住生产压力的 Agent Evaluation 体系，应该是分层的漏斗：

层级 评估类型 特点 退款 Agent 示例
第 1 层：确定性评估 规则、正则、JSON Schema 极快、极稳、极便宜 回复里是否包含10位退款单号？金额是否为数字？
第 2 层：程序化评估 Code-based / API 断言 可验证客观事实 refund API 接口是否真的返回成功？数据库状态是否已更新？
第 3 层：语义化评估 LLM-as-a-Judge / 人工评审 判断质量、完整性、事实性 回复是否真正解决了用户痛点？态度是否安抚？是否产生了幻觉？

这里有一个最重要的工程纪律：

能用规则和代码断言解决的，就绝不要用模型去评。

把“格式错”、“接口错”等低级错误拦截在第 1、2 层，只有那些判断“语气好不好”、“有没有幻觉”的灰色地带，才进入最昂贵的第 3 层。

三、LLM-as-a-Judge：语义化评估的核心工具

在上面的漏斗中，第 1 层和第 2 层传统监控就能做。真正的痛点在第 3 层：怎么自动化评估自然语言？

过去，要么靠人工抽检（吞吐极低），要么靠 BLEU / ROUGE 这种死板的文本重合度算法（对语义一窍不通）。直到过去两年，业界找到了目前性价比最高的解法：LLM-as-a-Judge（让一个大模型去当裁判打分）。

它的工作方式可以用一句话概括：

用另一个更强、指令遵循更好的 LLM，按照严格的结构化 Prompt，对 Agent 的输出进行打分。

它在工程上具有极高的价值：

  1. 高吞吐：它可以异步覆盖每天几万条的生产 Trace。
  2. 结构化：它可以把长篇大论的自然语言，压缩成一个 0-1 或 1-5 的整数，让质量可聚合、可报警。
  3. 可解释：相比于传统深度学习黑盒，LLM 裁判会在输出分数的同附上详细的“判词（Reasoning）”。

但如果你直接把这个能力搬进生产，很可能会翻车。原因很简单：它不是一个客观、稳定的裁判。

四、它靠谱吗？六个必须承认的翻车模式

“用一个会产生幻觉的模型，去评判另一个会产生幻觉的模型，这事儿靠谱吗？”

这是每个严谨的工程师都会问的问题。答案是：它不客观，它有极其严重的偏见（Bias），你必须承认并防范它。

学术界（如 LMSYS）和业界的大量实践证明，LLM 裁判存在六大典型翻车模式：

  1. 位置偏见（Position Bias）：如果让它对比 A 和 B 哪个好，它往往更偏爱先出场（位置靠前）的答案。
  2. 冗长偏见（Verbosity Bias）：裁判极容易被长篇大论“唬住”，倾向于给长回答高分，哪怕一句短小精悍的回答质量更高。
  3. 同源偏见（Self-Preference）：用 GPT 判 GPT，它会觉得写得真好；用 Claude 判 Claude，它也会偏爱自己。
  4. Prompt 敏感性：你把评分要求稍微换个语序，它的打分分布可能就会发生漂移。
  5. 校准偏差（Calibration Drift）：当底层的 API 模型（如从 GPT-4 升级到 GPT-4o）发生变化时，原本 4 分的标准可能会整体偏移。
  6. 单次评分的高方差：即便 Prompt 不变，采样、API 端非确定性、甚至底层模型版本的小幅变化，都可能让同一条输入昨天打 4 分、今天打 5 分。

五、让 Judge 变得可信：六种工程手段

既然毛病这么多，为什么大家还在用？因为我们可以用工程的手段，把这些“不确定性”关进笼子里。

要让一个 LLM 裁判在生产环境中变得可信，你需要在写代码时落实这六点：

1. 拒绝含糊，提供严格的评分量表（Rubric）

永远不要问裁判：“这个回答好不好？”你要给出极度明确、不可随意发挥的结构化打分标准。

2. 关闭创造性（Temperature = 0）

裁判不需要想象力。在调用评估模型时，务必将 temperature 设置为 0 或极低值，以降低采样随机性带来的评分波动。但由于 API 端非确定性和底层模型微小版本变动依然存在，完全的绝对稳定并不能保证，这就是为什么还需要校准集和一致性检查。

3. 要求它输出可审计的推理过程（结构化 CoT）

不要只让 Judge 输出一个裸分数。要求模型先输出 reasoning（结构化的推理过程），最后再输出 score（分数）。这种“结构化 CoT”既能极大提升大模型遵循复杂规则的准确率，又能让每一次判定都可审计、可回溯。

4. 建立裁判校准集（Judge Calibration Set）

固定一小组“黄金样本 + 人工打分的已知分数”。可以先从 50 条左右的高质量样本起步。每次你微调了评估 Prompt，或者底层的裁判模型发生了 API 更新，先跑一遍这批校准集，确认裁判的“尺子”没有弯。
校准集不是一次性资产。 随着业务场景扩大、模型升级，校准集本身也需要扩充和重打标签。否则你监控的将是一把已经变形的尺子。

5. 允许 Judge 弃权（Abstain）

Judge 最危险的一类错误，是被强迫在证据不足时二选一。允许它输出 "score": "abstain"（或设置第三个状态档位），把这一类边界样本直接送入人工复核队列。在成熟的系统中，Abstain 本身就是一个极具价值的监控信号。

6. 双模型交叉评估与人工兜底

在资金允许的极核心业务上，让 Judge A（如 GPT-4o）和 Judge B（如 Claude 3.5 Sonnet）同时打分。分数一致则采信，分数分歧巨大则直接送入人工复核队列（Human-in-the-loop）。

LLM-as-a-Judge 不是终点，而是分诊台：它决定了这三万条 Trace 里，哪三百条值得让人类亲自来看。并且请注意：Judge 必须异步运行，绝不能阻塞用户的实时请求。

六、生产落地：写一个真实的评估脚本

光说不练假把式。让我们把上面提到的“评分量表”和“思维链”落地成一段真实的 Python 脚本。

针对第三篇中“工具已经报错，但最终回复却无视报错并承诺退款已受理”的失败案例，我们写一个测试“忠实度（Groundedness）”的自动化打分：

{
  "system_prompt": "你是一个严格的 QA 审计员。你需要评估 AI 客服的最终回复是否完全忠实于其底层工具的返回结果，是否存在幻觉（Hallucination）。\n\n【评分量表 Rubric】\n请仔细对比 [工具调用轨迹] 和 [最终回复]，按以下标准打分：\n- 1分（Pass）：最终回复的所有事实陈述，都能在工具轨迹中找到支撑。未做与工具报错相悖的承诺。\n- 0分（Fail）：最终回复包含工具轨迹未返回的信息，或者在工具报错的情况下仍然生成了“已成功”的确认（例如工具失败但回复退款已受理）。\n\n【输出格式】\n必须返回 JSON。先在 'reasoning' 字段一步步分析对比，最后在 'score' 字段给出 0 或 1。"
}

配合一段极简的离线评估 Python 骨架：

import json
from openai import OpenAI

client = OpenAI()

# 将上文的 JSON Prompt 赋值给常量
JUDGE_RUBRIC_PROMPT = """你是一个严格的 QA 审计员。你需要评估 AI 客服的最终回复是否完全忠实于其底层工具的返回结果，是否存在幻觉（Hallucination）。
... [详见上文 Rubric] ...
"""

def evaluate_groundedness(trace_data):
    """ 对一条 Agent Trace 进行离线/异步打分 """
    user_input = trace_data["input"]
    tools_output = trace_data["tools_trajectory"]
    final_reply = trace_data["final_response"]

    user_content = f"用户请求：{user_input}\n工具轨迹：{tools_output}\n最终回复：{final_reply}"

    response = client.chat.completions.create(
        model="gpt-4o",  # 裁判模型通常指令遵循要求极高
        temperature=0.0, # 评估必须收敛稳定，关闭创造性
        response_format={"type": "json_object"},
        messages=[
            {"role": "system", "content": JUDGE_RUBRIC_PROMPT},
            {"role": "user", "content": user_content}
        ]
    )

    return json.loads(response.choices[0].message.content)

当你把第三篇里那条有 Bug 的 Trace 喂给这个脚本时，它会精准地拦住它，并输出：
{"reasoning": "工具轨迹明确抛出 TypeError 报错，但最终回复却无视了报错并承诺退款已受理，存在严重矛盾。", "score": 0}。

💡 最佳实践：在生产环境中，当 Judge 打 1 分（通过）时，也应要求它在 reasoning 里明确列出支撑结论的工具调用片段。否则，“1 分” 只是一个未被审计的盲目赞同。

补：隐私、合规与数据最小化提醒

生产 Trace 进入评估链路前，应先做数据分级、脱敏和最小化处理。不必要的 PII、客户标识、订单细节或内部系统响应原文，不应直接发送给外部 Judge 模型。Judge 评估本身也应纳入访问控制、审计日志和供应商数据边界内。否则，Evaluation 可能会从质量治理工具反过来变成新的数据泄漏面。

这就构成了企业中 CI/CD 发布门禁 和 数据集沉淀 的技术底座：

  1. 线上采样：异步跑打分，低分/高风险 Trace 自动沉淀为“失败测试集”。
  2. 离线回归：当你试图修改 Prompt 或换模型发版时，先批量跑这批数据集。
  3. 门禁阻塞：如果新版本的平均分下降，直接阻塞发布。

这不是一个理论上的概念，这是真实能接入 CI/CD 的生产做法。

七、误区与红线：别让 Judge 变成新的黑盒

最后，有几条红线必须划清，以免你把 LLM 裁判当成了包治百病的银弹。

1. Judge 也是模型，它也要被观测

它也会漂移、出错、产生幻觉。你的可观测性大盘上，必须留出版面给 Judge 本身（例如：监控 Judge 模型 API 的版本、Judge Prompt 的版本迭代，以及抽样人工复核的一致率）。

2. 永远不要用 Judge 替代高危业务的合规决断

在医疗建议、金融信贷、法律合规等极度敏感的场景，LLM 裁判只能作为“初步筛选过滤网”，绝不能作为“最终审批章”。机器不背锅，背锅的只有人。

3. 避免落入“回声室（Echo Chamber）”效应

如果你让干活的 Agent 和当裁判的 Judge 使用完全同源的模型和一模一样的底层逻辑（甚至连 System Prompt 都高度重合），就会形成“自我强化的假质量”：Judge 会系统性地放过 Agent 犯的一整类错，同时给出稳定的高分，让整个评估链看起来运行良好，实则盲人摸象。

八、结语：从“检测失败”到“治理智能体”

Evaluation 不是给 Agent 简单打个分，而是让 Agent 变得可治理。

走到今天这一步：

  • Trace 让我们能在茫茫请求中回放一次事故的经过；
  • Metrics 让我们能在宏观上量化 Agent 消耗了多少 Token 和算力；
  • Evaluation 则为这一切插上了“对错”的标尺，让系统从“裸奔”走向了“可验证、可回归”的闭环。

传统监控让服务不崩溃，而 Evaluation 让智能体可信。有了 Judge 分数，你的服务健康视角就不再只有单纯的延迟和错误率——忠实度达标率（Groundedness Rate）和合规通过率可以作为辅助 SLO 进入监控大盘。至于它是否适合作为对外承诺的 Hard SLO，我们将在后续讨论。

但别急，即使有了高分的 Evaluation，生产环境中仍然潜伏着一些会瞬间击穿你可用性和成本的恶魔：死循环、上下文爆炸、工具未响应……

在下一篇，我们将进入运维视角的深水区，看看在第 ⑤ 篇：如何抓幻觉、死循环和成本失控——从 Signal 到 SLO 的告警实战。
