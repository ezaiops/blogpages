读懂一条 Agent Trace：OpenTelemetry GenAI 语义拆解

2026 年 7 月 6 日 · 约 12 分钟阅读

“抓凶手”不能靠猜。当代码里混入大模型的自由意志，Debug 的第一步不再是看 Log，而是看 Trace。

这是《AI Agent 可观测性》系列的第三篇。前两篇我们确立了 Trace、Metrics、Evaluation 三层框架。今天，我们终于要见真东西了——撕开黑盒，看看一条 Agent 运行轨迹到底长什么样。

一、开篇故事：一次“完美”的客诉

退款客服 Agent 上线的第一周，你收到了一条愤怒的用户投诉：

用户：“三天前我就说了退款，你们的 AI 告诉我‘退款已受理’，但我到现在一分钱都没收到！”

作为负责人的你，立刻熟练地打开了传统的 APM 面板，通过 session_id 查到了那次请求。结果让你眉头一皱：

  • HTTP 网关返回 200 OK。
  • 订单数据库没有慢查询，也没有死锁。
  • 容器的 CPU 和内存完全正常。
  • 错误日志（Error Log）里干干净净。

在传统监控的世界观里，这是一次完美、健康、无懈可击的请求。但业务确实挂了，钱没退。

为了查明真相，你打开了刚接入的 Agent Observability 平台，调出了那次请求的 Trace（行为轨迹）。真相大白。

二、案发现场：一棵 Agent 行为树

💡 先立边界：为了方便理解，下面的 Trace 做了脱敏和简化；它不是某个工具原样导出的完整 JSON，而是一条生产级 Agent Trace 在可观测性面板中通常呈现出的核心结构。

在可观测性面板里，你看到了一棵由多个 Span（追踪跨度）嵌套而成的“行为树”。这就是那个退款请求的真实执行过程：

Trace: refund_agent_run (Total Duration: 3.2s)
├── 🔵 chat.completions (Model: gpt-4o)          [800ms]
│   ├── Prompt: "用户要求退款，订单号 12345..."
│   └── Output: ToolCall(name="query_order")
├── 🟢 execute_tool: query_order                 [150ms]
│   ├── Input: {"order_id": "12345"}
│   └── Output: {"status": "paid", "amount": 99.0}
├── 🔵 chat.completions (Model: gpt-4o)          [1.1s]
│   └── Output: ToolCall(name="create_refund")
├── 🔴 execute_tool: create_refund               [50ms] ❌ ERROR
│   ├── Input: {"order_id": "12345", "amount": "full"}
│   └── Output: "TypeError: amount must be a number"
└── 🔵 chat.completions (Model: gpt-4o)          [1.1s]
    └── Output: "您的退款已受理，请留意近三日账单。"

凶手找到了。 这是一个典型的“语义性失控”加上“幻觉”的连环车祸：

  1. 第一次调用模型：Agent 表现很好，决定先查订单（query_order）。
  2. 第二次调用模型：Agent 决定发起退款。但在组装参数时，大模型自作主张，把 amount 字段填成了字符串 "full"（全额），而不是 API 要求的数字 99.0。
  3. 工具执行报错：底层的 create_refund 工具是个严谨的 Python 函数，直接抛出了类型错误。
  4. 最坑的一步来了：大模型收到了工具报错的上下文，但后续的生成没有正确暴露这个失败，而是继续输出了“退款已受理”的安抚性幻觉回复。

这就是为什么 HTTP 是 200，但业务却失败了。

如果没有 Trace 把每次模型生成的 Prompt、工具调用的入参和出参全记录下来，这种在不同大模型思考节点之间发生的 Bug，根本无从查起。

三、剥开洋葱：OTel 怎么表达 Agent 行为？

你看懂了上面那棵树，但工程上有一个问题：如果每个框架都自定义一套数据格式，监控大盘根本拼不出这棵树。

这就是业界需要 OpenTelemetry (OTel) GenAI 语义约定 的原因。它提供了一套共享的“通用语言”：让不同框架、SDK 和后端在描述模型调用、工具调用、Token 用量和错误时，尽量使用一致的语义。

为了理解 OTel 的表达方式，我们可以把上面那个出错的工具调用，简化成一个“类 OTel Span”的结构。

⚠️ 注意：这是一段教学示意，保留的是 Span / Attributes / Events 的核心结构关系。不要直接把字段名照抄进生产代码，真实的字段（例如 gen_ai.tool.name 或 tool.name）会随 OTel 版本和具体探针的实现而变化，请以当前规范和所用库文档为准。

{
  "name": "execute_tool create_refund",
  "kind": "INTERNAL",
  "context": {
    "trace_id": "5b8e9f...",
    "span_id": "9a1c3d..."
  },
  "attributes": {
    "gen_ai.operation.name": "execute_tool",
    "gen_ai.system": "example-agent-framework",
    "tool.name": "create_refund",
    "error.type": "TypeError"
  },
  "events": [
    {
      "name": "tool.input",
      "attributes": {
        "content": "{\"order_id\":\"12345\",\"amount\":\"full\"}"
      }
    },
    {
      "name": "tool.output",
      "attributes": {
        "content": "TypeError: amount must be a number"
      }
    }
  ]
}

在这个结构中，有几个核心概念：

  1. gen_ai.operation.name：定义了这一步在干嘛。它是整个分析的骨架，常见的值有 chat（模型对话）、execute_tool 等。
  2. Attributes（属性）：挂载在这个跨度上的静态特征。如果是模型调用，这里还会有至关重要的计费指标：gen_ai.usage.input_tokens 和 output_tokens。
  3. Events（事件）：大文本（如工具调用的 JSON 入参、模型生成的长文本）往往不适合塞进属性，而是作为有时间戳的事件挂在 Span 之下。

四、极简动手：低侵入接入，而不是魔法零侵入

看到这里，你可能心里打鼓：“难道我要在每调一次模型、每写一个工具函数时，都手动去写 span.start()、手填这些 JSON 字段吗？”

答案是：不需要。越来越多主流 LLM/Agent 框架已经可以通过自动探针（Auto-Instrumentation）接入 Tracing。

以 Python 中的 LangChain / LangGraph 为例，下面代码展示了接入的思路：

# 示例：不同库的包名、类名可能随版本不同而变化，请以你使用的版本文档为准。
# 注意：可能是 LangChainInstrumentor 或 LangchainInstrumentor

from opentelemetry.instrumentation.langchain import LangchainInstrumentor

# 开启探针，对业务逻辑实现“低侵入”埋点
LangchainInstrumentor().instrument()

# 接下来，继续编写你原本的 Agent / Graph 业务逻辑
from langgraph.graph import StateGraph
# ...

在完成环境配置（例如开启采样和脱敏策略）后，Instrumentation 通常可以在底层默默拦截模型调用和部分工具调用，捕获 Token 和耗时，并发送给可观测性后端。实际的捕获范围，取决于你所用的 SDK、版本以及受控配置。

但这并不是毫无代价的“魔法零侵入”。当你把它推上生产环境时，必须越过下面这三个大坑。

五、生产环境避坑指南

1. PII、数据隐私与内容捕获策略

在上面的探针配置中，我们要澄清一个巨大的误区：不要假设探针默认是安全的。

不同探针库的默认行为并不一致。有些实现默认只抓取模型名、Token 消耗等元数据；但也有部分探针库（如 opentelemetry-instrumentation-langchain）默认会捕获完整的 Prompt 和模型输出。

⚠️ 红线警告：Prompt 和模型回复里往往包含用户的真实姓名、信用卡号、公司机密。

解法：在生产环境里，必须逐项确认所用 SDK / 探针的内容捕获开关（例如配置 TRACELOOP_TRACE_CONTENT=false）。要想看到我们在开篇破案时用到的工具入参和 Prompt 文本，通常需要显式且受控地开启。并且一旦开启，必须在数据发送出业务服务器前，按安全策略进行脱敏、截断，或只保留数据引用 ID，绝不能让敏感信息明文裸奔。

2. 高基数（High Cardinality）灾难

永远不要把你给大模型发的 Prompt 文本，或者动态生成的用户 ID，当成 Span 的 name 或直接设为可索引的 attribute（属性）。

可被索引的属性一旦具有极高基数（无限多的离散值），可观测性后端的数据库会瞬间爆炸，查询慢如蜗牛，账单也会飙升。

解法：Span Name 必须是低基数的常量（例如 chat、create_refund）；大段文本或动态内容，更适合放在受控的 Event 中、外部 Blob 存储中，或在 Trace 里仅留一个引用 ID。

3. 全量 Trace 与存储成本

Agent Trace 往往比传统 API Trace 大得多（包含多轮对话、检索文档、工具返回的大量 JSON）。

如果所有内容全量长期保存，成本极高。生产环境里的常见做法是：错误请求全量保留，正常请求采样；线上排障用的高精细度 Trace 只保留短周期，而进入回归测试集（Dataset）的失败样本才长期保存。

六、结语：不能只靠肉眼看录像

有了 Trace，我们就像拿到了案发现场的高清录像。现在，我们清楚地知道那个“退款已受理”，并不代表退款真的成功，而是一次工具失败后的错误确认回复。

但是，这引出了一个巨大的工程挑战：

我们不可能雇一堆人，每天去肉眼翻看成千上万条 Trace 树。

既然大模型会用流畅的自然语言包装错误，那我们能不能用另一个模型来做自动化的质量裁判？

下一篇，我们将进入这套框架里最具争议、但也最具威力的第三根支柱：怎么给“对不对”打分——从规则到 LLM-as-a-Judge。
