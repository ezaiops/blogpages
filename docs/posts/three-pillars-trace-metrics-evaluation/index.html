AI Agent 可观测性的三大支柱:Trace、Metrics、Evaluation

2026 年 7 月 4 日 · 约 18 分钟阅读

看见它做了什么,量化它跑得怎样,判断它做得对不对。

这是《AI Agent 可观测性》系列的第二篇。上一篇我们回答了"为什么传统 APM 不够";这一篇要回答:到了 Agent 时代,为什么光有日志、指标和链路还不够——那我们到底该观测什么。

一、从"系统没坏"到"Agent 做对了吗"

上一篇的结论是一句话:传统 APM 看得见"系统有没有坏",却不一定看得见"Agent 有没有做对"。

那么很自然的下一个问题就来了——

如果一个 Agent 的失败,不一定表现为错误码、超时或宕机,我们到底该观测什么?

答案不是多加几行日志,也不是再堆几个大盘。要把这件事讲清楚,得先把"观测什么"拆成三类互相不能替代的问题:

你想知道的 对应的能力
Agent 这一次到底做了什么? Trace(轨迹)
大量运行整体表现如何? Metrics(指标)
输出的内容到底对不对? Evaluation(评估)

这就是本文要讲的三大支柱。用一句话记住它们的分工:

Trace 记录行为,Metrics 量化运行,Evaluation 判断质量。

先做两个诚实的说明

第一,"三大支柱"是本文的讲解框架,不是官方术语。

OpenTelemetry 官方并不用 "pillars(支柱)"这个词,它用的是 signals(信号)——当前支持的是 Traces、Metrics、Logs、Baggage,另有 Events、Profiles 等还在开发或提案阶段[1]。所以严格地说:"三大支柱"是本文为了讲清 Agent 可观测性而搭的工程框架;在 OpenTelemetry 语境里,Traces、Metrics、Logs 这些叫遥测信号(telemetry signals)。后面我们说"支柱",指的都是这个框架意义上的。

第二,把 Trace / Metrics / Evaluation 列为三大支柱,不等于把 Logs 扔了。

细心的读者会发现:传统常说的"三大"是 Logs / Metrics / Traces,怎么到了这里,Logs 换成了 Evaluation?

这不是说日志在 Agent 系统里不重要。日志仍然是审计、异常记录、安全追踪和排障的底层证据——而且在 LLM 场景里,很多平台会把 tracing 组织成"每次请求的结构化记录",记录 prompt、模型回复、token 用量、延迟,以及中间的工具与检索步骤[2]。

准确的说法是:

Logs 仍是底层证据;Trace / Metrics / Evaluation 是本文用来组织 Agent 可观测性的上层框架。

我们把重点放在这三件事上,是因为它们对应了 Agent 时代三个最关键、也最容易被传统监控漏掉的问题。下面逐个展开。

二、一个贯穿全文的例子:退款客服 Agent

为了不让三大支柱停留在抽象概念,我们用一个虚构、但很现实的例子,贯穿后面三节。

用户:我上周被重复扣费了,帮我退款。

一个 Agent 处理这句话,一次运行(run)大致会经历:

  1. 理解用户意图(这是一个"退款请求");
  2. 检索退款政策(能不能退、怎么退);
  3. 查询订单系统(确认确实重复扣费);
  4. 判断是否符合退款条件;
  5. 调用退款接口(refund API);
  6. 生成给用户的回复;
  7. 被评估系统判断:这次到底有没有真正把事办对。

记住这七步。接下来:

  • Trace 负责看清"这一次"每一步发生了什么;
  • Metrics 负责看"很多次这样的退款"整体表现如何;
  • Evaluation 负责判断"这一次"回答和处理是否真的正确。

三、Trace ｜ 事实层:看见一次 Agent Run 的行为链

三大支柱里,Trace 是事实层——它记录一次 Agent run 到底怎么走的。没有它,后面的一切判断都没有落脚点。

1. 结构像 APM,但语义重心变了

Agent 的 trace 复用了 APM 那套 trace / span 结构,但装的东西换了:

APM trace 追踪的是:请求穿过了哪些服务。

Agent trace 追踪的是:Agent 为完成目标,采取了哪些行为。

APM 的 span 里关心的是"服务 A 调服务 B、耗时多少、有没有报错";Agent 的 span 里则要关注 prompt、模型回复、token 用量、工具调用、检索步骤这些行为语义。

⚠️ 需要提醒:prompt 和模型回复常常包含用户数据、PII 或商业敏感信息。在真实生产环境里,这些内容通常要按安全策略采样、脱敏、截断,或只记录摘要 / 引用 ID,而不是无条件全量明文落库。

2. 它是一棵"行为树"

还是用退款的例子。一次运行的 trace,大致长这样:

Agent Run: refund_request
├── 用户输入
├── 意图理解
├── 检索:退款政策
├── 工具调用:query_order(查订单)
├── 工具调用:create_refund(发起退款)
├── 模型回复:生成给用户的话术
└── 评估结果:这次算成功吗?

这棵树让你第一次能回放一次 Agent 运行:它在第几步检索了什么、调了哪个工具、传了什么参数、拿回什么结果、在哪一步开始跑偏。

(这里只给示意结构,不上真实字段。一条 trace 在标准里到底该记哪些字段,是下一篇的主题。)

3. 呼应上一篇:行为证据,不是内心独白

上一篇我们强调过一句话,这里要再说一遍,因为它是理解 Trace 的关键:

Trace 让我们看到 Agent 的行为证据,而不是读懂模型的"内心独白"。

可观测性读不懂神经元里在想什么;它能做的,是把外部可见的行为——选了哪条路、用了什么上下文、调了什么工具——完整记录下来。判断"对不对",是第三根支柱 Evaluation 的事;Trace 只负责把"发生了什么"如实摆在你面前。

🔗 下一篇讲 OpenTelemetry GenAI 语义约定时,我们会看这些行为证据如何被标准化地记录。

四、Metrics ｜ 趋势层:量化性能、成本、稳定性和行为

Trace 适合看单次问题;但你不可能一条条翻 trace。要看"很多次退款整体表现如何",就需要 Metrics——把海量运行聚合成趋势。

Agent 的指标可以分成三层,比简单的"新指标 vs 旧指标"更清楚:

类型 指标示例 说明
继承自 APM 端到端延迟、吞吐、错误率、资源饱和度 仍然要,用来判断服务本身是否稳定
被 Agent 改造 延迟拆成模型延迟 / 工具延迟 / 检索延迟、重试次数 还是运行指标,但要拆到 Agent 的每一步
Agent 原生新增 Token 用量、每次运行成本、工具调用次数、循环步数、检索命中率与相关性评分的聚合、上下文占用 用来盯成本、行为异常和质量风险

注意:像"检索相关性"这类质量信号,通常先由规则、模型评估或人工标注产生分数,再被聚合成 Metrics 来看趋势——它其实跨在 Metrics 与 Evaluation 之间。

中间那一层特别值得注意。以延迟为例:传统 APM 的 latency 是"单次 API 响应耗时",一个数就够了;但一次退款任务可能包含多次模型调用、多次工具调用、检索和重试,所以 Agent 的延迟必须拆开——到底慢在模型、慢在工具,还是慢在检索?不拆,你就只知道"慢",不知道"为什么慢"。

这一节直接承接上一篇的单位经济性(unit economics):

在 Agent 系统里,一次任务的成本不只来自 CPU 和内存,还来自 token、模型调用、工具调用、检索和重试。所以 Metrics 不只是稳定性指标,也是单位经济性指标。

放回退款的例子,Metrics 要能回答这些问题:

  • 平均一次退款任务,调了几个工具?
  • p95 端到端耗时是多少?最慢的是哪个工具?
  • 每次退款平均烧多少 token、多少钱?
  • 有没有出现"循环步数"异常升高——某些请求 Agent 反复兜圈子?

(OpenTelemetry 把 Metrics 定义为"运行时捕获的度量"[1];Langfuse 也明确建议追踪成本与 token 用量[2]。这些是 Agent 指标体系的公开依据。)

五、Evaluation ｜ 判断层:它做得对吗?

前两根支柱能告诉你 Agent 跑得快不快、贵不贵、稳不稳。但它们都回答不了那个最要命的问题——就像第一篇提到的那个场景:一个客服 Agent 一本正经地编造了并不存在的退款政策,延迟正常、没有报错、资源健康,唯独答案是错的。

Metrics 告诉我们 Agent 跑得怎么样;Evaluation 才告诉我们它做得对不对。

这就是 Evaluation 的位置。这里要非常小心地说清楚它和传统手段的关系——它不是传统监控的替代品,而是 Agent 时代新增为"一等公民"的质量判断层。

还要说清楚一点:Evaluation 不是"真理机器"。它在给定业务规则、参考答案、评分标准(rubric)或工具返回结果的前提下工作,把"对不对"变成一个可重复、可追踪、可回归的判断过程——而不是天然掌握绝对真相。

1. 它和传统的"质量"手段有什么不同

传统 APM / SRE 里其实早就有一堆和"质量、体验"相关的东西。Evaluation 不是要否定它们,而是补上它们够不着的地方:

传统手段 衡量什么 和 Agent Evaluation 的区别
SLO / SLI 服务目标是否达标 主要看可用性、延迟、错误率等服务表现
合成监控(Synthetic Monitoring) 预设脚本能不能走通 适合确定性断言;开放式 LLM 输出往往没有唯一标准答案,难以只靠脚本判断质量
Apdex / RUM 用户体验或性能满意度 多是体验代理,不直接验证回答的事实对不对
业务 KPI 业务结果趋势 能衡量结果,但通常解释不了单次输出为什么错

它们大多衡量的是服务表现、用户体验或业务结果。而——

Agent Evaluation 衡量的是:一次输出、或一次任务的完成过程本身,是否正确、完整、相关、有据可依、符合政策和安全要求。

2. 评估有哪几种

Evaluation 不是只有一种打分方式。按退款客服的例子,可以分成五类:

评估类型 评估什么 退款案例中的例子
规则评估(Rule-based) 格式、字段、禁词、schema 回复里是否带上了退款单号
代码评估(Code-based) 可程序化验证的结果 refund API 是否真的返回成功
LLM 当裁判(LLM-as-a-Judge) 语义质量、完整性、相关性 回复是否清楚解释了退款条件
人工评审(Human Review) 高风险、复杂业务判断 大额退款建议是否需人工复核
多轮评估(Multi-turn) 多轮任务是否真正完成 用户最后有没有拿到正确处理结果

(以 Langfuse 的评估文档为例,它把 LLM-as-a-Judge、人工标注、自定义评估流程组合起来,用于衡量质量、语气、事实准确性、完整性等维度[3]。)

🔗 第四篇我们会专门讲 LLM-as-a-Judge:它怎么打分、什么时候可靠、什么时候会翻车。

3. 评估是"闭环的入口"

最后一点最关键。Evaluation 的价值,不只是给一次回答打个分:

它把失败样本沉淀成数据集,把线上暴露的问题转化为离线可回归的测试。

也就是说,评估既可以在线上对真实 trace 打分,也可以在发布前离线跑;有价值的例子会被收集成数据集,用来做实验、对比改动、防止下次发布把已经修好的东西又改坏[3]。这一点,为下一节的"闭环"埋好了伏笔。

六、三者如何形成闭环:观测的终点不是大盘

到这里,三根支柱都讲完了。但它们真正的威力,不在于各自单独存在,而在于串成一个回路:

Metrics 发现趋势         (退款成功率突然掉了 / 成本翻倍)
      ↓
Trace  定位到具体运行     (是哪一批请求、卡在了哪一步)
      ↓
Evaluation 判断对错       (这些输出到底该不该算失败)
      ↓
失败样本进入 Dataset      (沉淀成可复现的测试集)
      ↓
改 Prompt / 工具 / 模型 / 流程
      ↓
下一轮继续观测           (验证改动是否真的变好)

这就是为什么说,Agent 可观测性的终点不是一个好看的大盘,而是一个持续改进的闭环。

本篇最该记住的一句话:

没有 Trace,线上失败的 Evaluation 往往缺少过程证据;没有 Metrics,Trace 缺少全局视角;没有 Evaluation,可观测性只能说明"发生了什么",不能说明"做得好不好"。

三根支柱,缺一根,回路就断了。

七、落地建议:如果从零开始,先采什么

⚠️ 这一节是经验建议,不是行业标准。如果你要从零给一个 Agent 搭可观测性,可以按这个顺序逐步补齐,而不是一开始就全上。

阶段 建议采集 目的
Day 1 trace_id / session_id、agent 名称与版本、模型名、prompt 版本、输入/输出 token、延迟、工具名/参数/结果/错误、最终回复、基础技术成功/失败标记(以及可选的业务成功/失败标记) 让一次运行能回放、能定位
Week 1 每次运行成本、重试次数、循环步数、检索 query 与命中文档、是否转人工、失败分类、简单评估分数 让趋势和失败模式可分析
成熟阶段 多轮任务评估、多 Agent 交接(handoff)轨迹、长期记忆读写、线上评估采样、trace 转数据集、CI 回归评估 进入持续改进闭环

原则只有一句:别追求一步到位,先让一次运行能被回放、能被打分,再慢慢往上加。

八、结语:下一篇进入 OpenTelemetry GenAI 标准

到这里,我们已经有了 AI Agent 可观测性的基本框架:

Trace 记录行为,Metrics 量化趋势,Evaluation 判断质量。

但还有一个问题没解决——这些信号,到底该用什么标准格式来表达?

如果每个框架、每个平台、每个团队都自己定义字段,Agent 可观测性很快就会变成一堆新的数据孤岛:你在 A 平台记的 trace,换到 B 平台就读不懂。

所以下一篇,我们进入 OpenTelemetry GenAI 语义约定:一次 LLM 调用、一次工具调用、一次 agent invocation,在标准里到底应该长什么样。

框架已经立好,下一篇,我们给它配上通用的"语言"。

参考与核验来源

  1. OpenTelemetry — Signals:OpenTelemetry 以 signals 组织遥测数据,当前支持 traces、metrics、logs、baggage(events、profiles 处于开发/提案阶段);并将 metrics 描述为"运行时捕获的度量"。 ↩
  2. Langfuse — LLM Observability & Application Tracing:application tracing 会记录每次请求的结构化信息,含 prompt、模型回复、token 用量、延迟,以及中间的工具与检索步骤,并建议追踪成本与 token 用量。 ↩
  3. Langfuse — Evaluation of LLM Applications:evals 为 LLM 应用行为提供可复现的检查,可对线上 trace 打分、把有价值的样本沉淀成数据集、跑实验对比改动,并组合 LLM-as-a-Judge、人工标注与自定义评估流程。 ↩
